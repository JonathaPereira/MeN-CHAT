# Conversas privadas reais

Para novos amigos, use agora [Convites pelo aplicativo](convites-pelo-aplicativo.md): configuração única e ativação automática após OTP. O provisionamento manual abaixo documenta a entrega inicial e não é necessário para cada convite.

Esta entrega liga texto privado ao PostgreSQL e Supabase Realtime. Grupos, anexos, áudios, digitação, recibos, presença online e convites de cadastro pelo app ainda são demonstrações ou etapas futuras. O indicador “Ao vivo” informa o canal de atualização, não se outra pessoa está online.

1. No projeto MenChat, SQL Editor → New query, aplique uma vez [20261104000300_private_chat.sql](https://raw.githubusercontent.com/JonathaPereira/MeN-CHAT/main/supabase/migrations/20261104000300_private_chat.sql). Mantenha as migrações anteriores. O SQL cadastra mensagens na publicação `supabase_realtime` quando ela existe. No painel Database → Replication/Publications, confira que `menchat_messages` está habilitada para Realtime; se a publicação não existir, configure esse recurso no painel antes do teste ao vivo.
2. Baixe o ZIP atualizado, copie localmente seu `.env.local` para a nova pasta, instale com `npm ci --cache "$LOCALAPPDATA/npm-cache"`, faça `npm run build` e inicie `npm start -- --hostname 0.0.0.0 --port 3001`. Pare o servidor antigo antes.
3. Abra http://127.0.0.1:3001/conta/chat ou clique em “Abrir conversas reais” na conta. Sua conta precisa estar ativa. O chat antigo `/conversas` continua fictício.
4. Para testar entre duas pessoas, prepare uma segunda identidade no painel Auth com Auto Confirm, configure o template de código como no guia de primeiro acesso e peça ao titular para verificar o OTP/definir senha. Somente depois, o proprietário do projeto pode aplicar [setup-member.sql](https://raw.githubusercontent.com/JonathaPereira/MeN-CHAT/main/supabase/setup-member.sql), substituindo o placeholder pelo e-mail correto. A confirmação administrativa do Auth não prova posse da caixa; o operador precisa acompanhar o OTP antes de ativar. Não use setup-owner para a segunda conta. Estes scripts são ações administrativas manuais, não um fluxo público de convite.
5. Na segunda conta, abra `/conta` e copie seu código. Na primeira conta, clique Nova conversa por código, digite esse código e abra. Use uma janela anônima/outro navegador para a segunda identidade; duas abas normais compartilham a mesma sessão. Na outra conta, a conversa aparece em até cinco segundos. Texto enviado deve aparecer ao vivo; se o canal falhar, há consulta periódica a cada cinco segundos e retomada ao focar a janela.
6. Recarregue, saia e entre: o histórico deve continuar. Teste texto longo, acentos, quebras de linha, celular, mensagens antigas (50 por página), perda de rede e tentativa novamente. Envios repetidos após falha usam o mesmo UUID enquanto o texto/conversa não mudarem. A confirmação mostrada é de gravação no servidor; não é recibo de leitura.
7. Uma terceira conta, inclusive admin, não deve conseguir consultar ou inserir mensagens naquele privado por API. Conta desativada perde acesso no banco; dados já carregados em memória não podem ser recuperados remotamente. A lista é revalidada periodicamente e limpa conversas que perderem autorização. O interlocutor ativo preserva histórico, mas não envia para conta desativada.

## Proteções

Privado tem exatamente dois participantes fixos, sem UPDATE/DELETE público. Mensagens só aceitam autor igual ao JWT e participação válida; timestamps e sequência vêm do banco. Não há chave administrativa no cliente, permissões de leitura global para admins ou canal público que distribua todas as mensagens. Postgres Changes exige SELECT/RLS para cada destinatário. A API pública de abrir conversa retorna apenas um UUID e respeita busca por código; nomes são retornados somente para conversas existentes. Códigos ocultos não saem na listagem. A busca permite 15 tentativas por minuto por conta ativa, inclusive quando não acha o código; isso é imposto no banco.

A verificação `supabase/verify.sql` valida a base de contas. Para esta entrega, confira o registro `20261104000300_private_chat` em `menchat_private.schema_migrations` pelo SQL Editor e realize o teste entre duas contas acima. Não há promessa de criptografia ponta a ponta.

`npm run test:db` verifica SQL e autorização em PostgreSQL isolado com identidades simuladas. Não valida o servidor Realtime hospedado ou entrega entre dispositivos. O teste com seu projeto é necessário; as credenciais locais do Windows não estão disponíveis neste ambiente de desenvolvimento.
